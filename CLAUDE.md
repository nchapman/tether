# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tether is a low-latency open-source remote desktop in Rust. Two binaries (`tether-host`, `tether-client`) and nine library crates in a Cargo workspace. Status is pre-MVP. The Linux↔Linux path is the most exercised — VAAPI hardware encode, PipeWire DMA-BUF capture, wgpu present — and now negotiates HEVC Main 4:4:4 at both 8-bit (packed `XYUV` dma-buf input via `Yuv444DmaBuf`) and 10-bit (packed `XV30` dma-buf input via `Bgra2Xv30DmaBuf`) when both ends support it, for desktop-quality chroma fidelity over the 4:2:0 baseline. **macOS host and macOS client are both wired end-to-end**: ScreenCaptureKit capture (`tether-capture::macos`) → VideoToolbox encoder (`tether-codec::videotoolbox`) → IOSurface zero-copy hot path (`encode_iosurface_frame` in the host binary); on the client, VideoToolbox decode → IOSurface → Metal → wgpu import covers HEVC Main, Main10, and Main 4:4:4 8/10-bit (verified by the four `iosurface_zero_copy_roundtrip_*` hardware tests in `tether-render/src/iosurface_test.rs`). CGEvent input injection rides through the shared `inject::enigo_backend`. Windows backends and audio are still deferred.

Toolchain is pinned via `mise.toml` (rust 1.95). MSRV in `Cargo.toml` is 1.85.

## Common commands

All wrapped by `make` — `make help` lists every target. Underlying cargo invocations:

- `make build` — `cargo build --workspace`
- `make test` — `cargo test --workspace --lib` (no hardware required)
- `make test-hw` — `test-correctness` + `bench`; needs a working VAAPI + Vulkan box
- `make test-correctness` — runs the `#[ignore]` hardware tests in `tether-codec`, `tether-render`, `tether-gpuconvert`
- `make bench` — `cargo test -p tether-codec --lib bench -- --ignored --nocapture --test-threads=1` (the `--test-threads=1` is required: parallel cells contend for the same VAAPI device and make timings meaningless)
- `make probe` — prints which VAAPI codecs build on this host
- `make clippy` — advisory (pre-existing warnings exist, mostly in `tether-gpuconvert`)
- `make release` — release build of host + client only

Single test: `cargo test -p <crate> <test_name>`. Hardware-gated tests are `#[ignore = "requires …"]` — add `-- --ignored` and the test name to run one.

## Architecture orientation

`docs/ARCHITECTURE.md` is the source of truth; read it before non-trivial changes. The big picture:

- **`tether-protocol`** has zero I/O. It's the wire contract both sides speak — control messages (bincode, reliable), P-frames + cursor position (unreliable datagrams), **IDR keyframes (reliable per-keyframe uni streams)**, input (reliable stream). Forward-compat hooks: hello extension map with reverse-DNS keys (`tether.cap.*` follows echo-to-accept), `ControlMessage::Extension { key, payload }` escape hatch, `VideoFrameMetaEnvelope` versions per-frame metadata.
- **The hot path is zero-copy on both sides.** Host: PipeWire DMA-BUF → `tether-gpuconvert` (BGRA→NV12 compute pass into a single shared dma-buf with R8 Y + Rg8 UV planes at offsets; luma row pitch and height are pre-aligned to 64 bytes / 16 rows respectively so libva-intel-driver's DRM_PRIME importer doesn't mis-read the dma-buf — see `shared_nv12.rs`) → `tether-codec::vaapi` (`av_hwframe_map` DRM_PRIME→VAAPI) → `FrameFragmenter` → QUIC. P-frame fragments ride unreliable datagrams; IDR keyframes ride a fresh QUIC uni stream per IDR (one length-framed `VideoPacket::First { fragment_count: 1, ... }` carrying the whole encoded body, with codec extradata prepended for self-decodability). Client: `tokio::select!` between datagram and uni-stream paths → defragment → **dedicated `tether-decode` `std::thread`** (`av_hwframe_map` of the VAAPI surface) → `vaExportSurfaceHandle` per frame → `tether-render` imports both planes as wgpu textures, NV12→RGB matrix in the fragment shader. The decoder→renderer handoff is a `LatestFrame` single-slot drop-oldest cell so the renderer always pulls the freshest frame.
- **Cross-platform additivity** is done via two type seams. `CapturedFrame::Gpu(GpuCapturedSource)` and `GpuEncoderFrame` are cfg-gated **per variant** (`#[cfg(target_os = "linux")] DmaBuf(...)`, `#[cfg(target_os = "macos")] IOSurface(...)`), so matches stay exhaustive without a catch-all and adding a third backend means a new variant + a new backend module — not a refactor of the call sites. The opaque `GpuResourceGuard` (re-exported as `GpuCapturedGuard` / `GpuFrameGuard`) keeps backend lifetime-extension types from leaking through the public API. macOS-host concretely: ScreenCaptureKit hands NV12 IOSurfaces straight to VideoToolbox via `CVPixelBufferCreateWithIOSurface` — no gpuconvert step, no `BridgeState`, no chroma-aware dispatch (SCK is 4:2:0-only and the macOS encode probe rejects non-Yuv420 profiles up front).
- **Four end-to-end invariants:** (1) clock sync via handshake-measured `MonoNanos` offset + per-fragment `HostFrameTiming` stamps; (2) `stream_epoch: u32` bumped on any resolution/encoder restart, defragmenter drops cross-epoch fragments; (3) on-demand IDR via `ControlMessage::ForceIdr`, coalesced through an `AtomicBool` swap. GOP is long (~240); IDRs are request-driven, not cadence-driven; (4) every IDR is self-decodable — VAAPI encoder uses `AV_CODEC_FLAG_GLOBAL_HEADER` so codec parameter sets (SPS/PPS/VPS) live in `extradata`, and `drain_encoder` prepends them to every keyframe packet at send time. Without this, a client that loses the first IDR or rebuilds its decoder mid-session is stuck.

## Conventions that aren't obvious from grep

- **`HostFrameTimingBuilder` is typestate.** Skipping a stage panics — that's the contract. New host-pipeline stages add a `should_panic` test for the skip case.
- **Wire round-trip first.** Any new protocol message gets a unit test in `tether-protocol/src/lib.rs#mod tests` that asserts every field round-trips. Tagged-enum additions also get a forward-compat probe (hand-craft a "future" byte sequence, assert old code errors cleanly — see `unknown_client_hello_variant_fails_decode`).
- **Hardware tests are `#[ignore]`, not deleted or runtime-skipped.** Ignore message names the requirement (`vainfo`, the Vulkan extension, etc.) so it's obvious whether a given box should run them.
- **Hardware round-trip tests are where real bugs surface.** This is a project-specific convention I keep getting wrong. Every render-side bug we've hit (R16Unorm feature opt-in missing, `'x420'` fourcc not in renderer accept set, encoder/decoder fourcc-table drift) lived in code with **zero hardware test coverage**. The probe layer catches encoder/decoder asymmetries because the probe itself round-trips; the renderer side runs on parallel tables that get exercised only by manual sessions. Treat probe-pass as half-credit at best.
  - **Before claiming a new profile / chroma / bit-depth / fourcc / feature works**: confirm a hardware test takes a real artifact through the full chain you touched. For encode-side changes: `videotoolbox_round_trip_chroma_matrix` (macOS, `videotoolbox/tests.rs`) or one of `hevc_main444_dmabuf_roundtrip` (8-bit XYUV) / `hevc_main444_10bit_xv30_dmabuf_roundtrip` (10-bit XV30) (Linux, `vaapi/tests.rs`). For renderer changes: `iosurface_zero_copy_roundtrip_*` (macOS, `tether-render/src/iosurface_test.rs`) covers HEVC Main, Main10, Main 4:4:4 8-bit, and Main 4:4:4 10-bit through VideoToolbox → IOSurface → Metal → wgpu; the Linux harness in `tether-render/src/test_harness.rs` + `dmabuf_test.rs` drives the **production multi-pass renderer** (`Gpu::new_headless`, same `Bgra8UnormSrgb` blit target as the live swapchain) across a matrix of `(capture × encode × surface)` dims for H.264 4:2:0, HEVC Main, HEVC Main 4:4:4, HEVC Main 10, and HEVC Main 4:4:4 10-bit. Adding a new cell is a `RoundtripCase` struct literal + an assertion call — no per-cell helpers. Primary metric is **geometric residual on a coordinate-encoded fixture** (`Fixture::CoordEncoded` writes a smooth-gradient `(x, y)` encoding so the harness can recover stride/UV-addressing drift directly); SSIM and BT.709 Y-PSNR are the secondary catch-net. On metric failure the harness writes readback/reference/diff/SSIM-heatmap PNGs + `metrics.txt` to `target/roundtrip-diagnostics/<case>/` (override via `TETHER_DIAGNOSTICS_DIR`).
  - **The matrix dimensions that must all be exercised together** are: (profile codec, chroma, bit_depth) × (encoder, decoder, renderer-import) × (platform). The probe covers the first two columns of the middle axis. The third column — renderer import of a real decoded surface — is fully covered on macOS via `iosurface_test.rs` and now covered on Linux via the `dmabuf_test.rs` harness (identity + host-scaler + client-upscale + surface-below-video + full-chain + `repro_shape` rows at H.264 4:2:0, HEVC Main, HEVC Main 4:4:4, HEVC Main 10, and HEVC Main 4:4:4 10-bit, modulo per-profile capability SKIPs on driver gaps — Intel iHD + Meteor Lake currently SKIPs all 10-bit cells; the 4:4:4 10-bit cell may *additionally* error with "expected 2 layers, got 1" on drivers where VAAPI exports the decoded surface as packed XV30 rather than biplanar 16-bit, which would require a new `RenderLayout::Packed1010102` import variant — see `gpu/import.rs:53`). The `repro_shape` cell (2880×1920 → 2160×1440 → 2560×1440, H.264 4:2:0) is the regression catch for the libva-intel-driver row-pitch bug above — its dim shape is a real HiDPI 2× session that broke pre-fix. **Three-layer bisect tests** (`tether-scaler/tests/hardware.rs::matches_reference_coord_encoded_left_edge`, `tether-gpuconvert/tests/scaler_roundtrip.rs::bgra_dmabuf_roundtrip_*` and `::imported_bgra_then_scaler_*`) split the harness's "somewhere in the host pipeline" verdict into (scaler isolation) ↔ (BGRA dma-buf round-trip) ↔ (scaler-on-dma-buf) so a future left-edge regression triages from the bottom up without re-running the full encoder/decoder/renderer chain.
  - **Cross-table consistency belongs in unit tests too.** `metal.rs::import_iosurface_textures`, `videotoolbox/probe.rs::expected_iosurface_fourccs`, `videotoolbox/encoder.rs::iosurface_fourcc_matches`, `capture::macos::sck_pixel_format_for_profile` all encode the same chroma/bit-depth → fourcc-family relation. A unit test that asserts they agree (without hardware) catches drift between the four tables before a hardware run.
  - **End-to-end session loopback covers the handshake layer.** `crates/tether-session/tests/loopback.rs` runs `HostSession::accept` ↔ `ClientSession::connect` through `tether_transport::test_support::DuplexControlChannel` (a `tokio::io::duplex`-backed `ControlChannel` impl gated behind the `test-support` feature on `tether-transport`). The clock-sync RTT/offset math, Goodbye-on-no-match, unknown-bit-depth refusal, host-lenient-vs-client-strict bit-depth asymmetry, and dropped-peer transport-error propagation all run in default `cargo test`. **The remaining gaps are everything past the handshake**: video fragmenter/reassembler under loss, IDR-signalling latency, decoder-thread restart recovery, render drop-oldest under backpressure. `InputChannel` and `VideoChannel` traits are defined in `tether-transport`; their duplex fakes land when the first test that needs one does.
- **Hard requirement on hardware codecs.** SW H264 is gated behind `cfg(test)`. The probe returns `NoHardwareCodec` with actionable diagnostics rather than falling back silently.
- **NV12 export is pinned to `DRM_FORMAT_MOD_LINEAR`.** Tiled modifiers don't have a portable shared-allocation contract that VAAPI's DRM_PRIME importer honours. Capture side advertises whatever modifiers the GPU importer can consume; export side is LINEAR-only. Don't try to "optimize" this without reading the comment in `tether-gpuconvert`.
- **DMA-BUF luma row pitch is force-aligned at the exporter** in all four bridges. `shared_nv12.rs`, `shared_p010.rs`, and `shared_yuv444.rs` align to 64-byte pitch + 16-row height (`align_up(width, 64 / bytes_per_luma_px)`). `shared_xv30.rs` aligns to 128-byte pitch (32 luma px at 4 B/px) + 32-row height — Intel HEVC 4:4:4 encode reads in 32×32 CTUs and at 4 B/px the analogous Intel pitch boundary lands at 128 bytes, twice the NV12 luma constraint. In every case the Vulkan image is built at the aligned dims, the wgpu textures wrap that image, the compute dispatch covers only the visible region (right-edge padding stays undefined), and VAAPI crops via declared frame width. Without this, libva-intel-driver mis-reads the dma-buf at non-aligned widths (e.g. 2160 px on HiDPI 2× displays for NV12): VAAPI assumes the pitch is aligned regardless of what the dma-buf reports, so each row's leftmost N luma columns alias into the previous row's padding. RADV/NVK already report ≥128-byte pitch by default so the alignment is a no-op there. **Permanent workaround** — the bug is in libva-intel-driver's hardware-side pitch alignment, not Mesa/Vulkan, and no upstream fix is expected. The structural regression test `convert_reports_64_aligned_y_stride_at_unaligned_width` (lib unit test in `crates/tether-gpuconvert/src/nv12_dmabuf.rs`) catches a reintroduction for NV12 without needing the encoder in the loop.
- **Bridge init failures mid-session are fatal.** A startup probe (`tether_gpuconvert::importable_dmabuf_modifiers`) verifies the wgpu+Vulkan+features chain before PipeWire advertises DMA-BUF. Runtime failures after that are device-loss/OOM — exit loudly with `Goodbye(InternalError)` rather than silently dropping every Gpu frame. Same contract on the encoder lazy-init path: if `probe_encoder` succeeds at handshake (128×128) but the real-dimension construction fails, send `Goodbye` before exiting the send loop.
- **Video profile negotiation is host-authoritative.** Client advertises decode capabilities via `tether.cap.video.decode-profiles` (bincode `Vec<VideoProfile>`); the host intersects against `tether_probe::host_encode_profiles()` and picks the best mutual match from a fixed `tether_probe::PROFILE_PREFERENCE` ordered HEVC 4:4:4 10-bit → HEVC 4:4:4 8-bit → HEVC 4:2:0 10-bit (Main10) → HEVC 4:2:0 8-bit (Main) → H.264 4:2:0 (universal floor). Result echoed in `tether.cap.video.encode-profile`; legacy clients still see the inline `ServerHelloV1::chosen_codec` / `chosen_chroma` fields. Capability discovery goes through `tether_probe::host_supported_profiles()`, which round-trips every profile through the full production chain (capture → bridge → encoder → decoder); `SupportStatus::Unsupported` carries a `PipelineStage` tag naming exactly which stage rejected the profile. The probe lives one crate above tether-codec because round-tripping the production chain needs the gpuconvert bridge, which tether-codec can't depend on without a cycle. Fixtures live in `crates/tether-probe/fixtures/probe/`. **Per-platform asymmetries**: macOS VideoToolbox has no HEVC Main 4:4:4 *encode* path at any bit depth (so macOS hosts never advertise 4:4:4) but M-series silicon decodes HEVC 4:4:4 to a `'444v'` NV24 IOSurface and Main 4:4:4 10-bit to `'xf44'`/`'P410'` — a Linux→Mac session can negotiate 4:4:4 (either bit depth) even though Mac→anything cannot. The renderer dispatches on a `RenderLayout` (Biplanar8 / Biplanar16 / PackedXYUV) derived from chroma + bit_depth + platform: Linux 4:4:4 8-bit uses packed XYUV through dma-buf; Linux 4:4:4 10-bit uses packed XV30 on the *encoder-input* side (gpuconvert bridge `Bgra2Xv30DmaBuf` writes Rgb10a2Unorm) but the renderer-import side assumes biplanar 16-bit (P410-style) on the decoded surface — driver-dependent and **unverified on hardware as of this writing**, see `gpu/import.rs:53` for the failure mode if a driver emits packed XV30 instead. macOS 4:4:4 uses biplanar NV24 (8-bit) or biplanar 16-bit (10-bit) IOSurface — same Y R8/R16 + UV Rg8/Rg16 shader as the 4:2:0 paths, just full-res UV. A chroma switch still requires the same encoder/gpuconvert/renderer rebuild path as a resolution change.
- **wgpu is pinned to a trunk SHA via workspace `[patch.crates-io]`** because `texture_from_dmabuf_fd` isn't released yet. All wgpu sub-crates (`wgpu-core`, `wgpu-hal`, `wgpu-types`, `naga`) must move together — if you add a workspace member pulling wgpu, it goes through the same patch. Drop the pin when wgpu cuts a release with the API.
- **Connection is abstracted behind role traits in `tether-transport`.** `ControlChannel`, `InputChannel`, `VideoChannel`, and `ConnectionInfo` are defined in `tether-transport::channel`; the concrete `Connection` impls all four. `tether-session` takes `Arc<dyn ControlChannel>` so the post-QUIC handshake is loopback-testable through `DuplexControlChannel`. The handshake is split across two trait methods (`recv_client_hello` returns `(ClientHello, t1)`; `send_server_hello` stamps `t0_echo` / `t1` / `t2` immediately before write) so the clock-sync stamps stay in the wire layer and profile-negotiation policy stays in `HostSession::accept`. Orchestration routes through the `HostHandshake` → `ClientHelloReceived` typestate (re-exported from `tether-transport`) which owns the `Arc<dyn ControlChannel>` across the two consume-by-value transitions — double-send and send-before-recv are uncompilable, not runtime bugs. App binaries pass `Arc<Connection>` to the recv tasks (video/input/datagram methods aren't on `ControlChannel`) and coerce a clone to `Arc<dyn ControlChannel>` for the session call only.

## Testing matrix

`docs/TESTING.md` has the per-crate breakdown. Headline: ~205 default-on tests (52 in `tether-protocol` alone) + ~58 `#[ignore]` hardware tests across `tether-codec`, `tether-render`, `tether-gpuconvert` (incl. the integration tests in `scaler_roundtrip.rs`), and `tether-scaler`. Default CI is `cargo build --workspace --all-targets && cargo test --workspace`; hardware runner (when it exists) adds `-- --ignored`. `cargo build --workspace --all-targets` is warning-free (gate on it); `cargo clippy --workspace --all-targets` is advisory today (pre-existing cast warnings in `tether-codec` and `tether-scaler/src/reference.rs`).
